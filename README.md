# WikiHMRU — вики техподдержки

Рабочая база знаний для команды техподдержки. Сайт поддерживает светлую и тёмную тему, поиск по всей базе, вложенные разделы без ограничения глубины, статьи из блоков, фотографии, историю правок и два уровня доступа.

## Что есть в вики

- **База знаний** — типовые инструкции.
- **Сложные случаи** — разбор нестандартных заявок.
- **Удалённый доступ** — устройства и ID AnyDesk / RuDesktop. Эти сведения видны читателям по умолчанию; любую запись или раздел администратор может закрыть.
- **Управление** — администратор создаёт, переименовывает, вкладывает и удаляет разделы, назначает роли сотрудникам.
- **Гибкая карточка** — заголовки, текст, код, заметки, списки, ссылки и фото в произвольном порядке. Блоки можно перемещать.
- **История** — предыдущие версии статьи, автор правки, дата и время; администратор может восстановить версию.

Читатель видит только открытые разделы и статьи. Администратор видит и редактирует всё. Если закрыт родительский раздел, его содержимое тоже скрыто от читателя. Эти правила действуют в базе Supabase через Row Level Security, а не только в интерфейсе.

## Локальный просмотр

Нужен Python 3; сборка и установка пакетов не требуются:

```bash
cd /workspace/WikiHMRU
python3 -m http.server 8000
```

Откройте `http://localhost:8000`. Пока [config.js](config.js) не заполнен, вики работает в локальном режиме: данные находятся только в браузере. В этом режиме доступен экспорт и импорт копии JSON. Это удобно для проверки оформления, но не подходит для совместной работы. Локальные фото ограничены 1,5 МБ из-за лимита хранилища браузера.

## Настройка общей вики

GitHub Pages публикует интерфейс, Supabase хранит общие данные, фото и учётные записи.

1. Создайте проект Supabase. В **Authentication** отключите публичную регистрацию: участников должен приглашать администратор. Настройте Site URL и Redirect URLs на будущий адрес GitHub Pages, чтобы ссылки приглашения открывали вики.
2. Выполните [supabase/schema.sql](supabase/schema.sql) в **SQL Editor**. Скрипт создаёт таблицы, правила доступа, приватное хранилище фото и начальные разделы: «Телефония», «Интернет», «МФУ и принтеры», «Битрикс», «1С», «Прочее».
3. Создайте свою учётную запись в Supabase Authentication → Users и один раз назначьте ей роль администратора в SQL Editor. Подставьте свой email в запрос:

   ```sql
   update public.profiles
   set role = 'admin'
   where email = 'ваш-email@example.com';
   ```

   Проверьте, что обновлена ровно одна строка. Следующих администраторов можно назначать на сайте в разделе «Управление».
4. В Supabase Project Settings → API возьмите **Project URL** и **publishable key** (или legacy `anon` key). Впишите их в [config.js](config.js). Это публичные параметры клиента. **Никогда не вставляйте туда service_role key, пароли или другие секреты.**
5. Отправьте файлы в ветку `main`. В настройках GitHub репозитория выберите Pages → Source → **GitHub Actions**. [Workflow](.github/workflows/pages.yml) опубликует сайт после отправки изменений.
6. Пригласите сотрудников через Supabase Authentication → Users. После первого входа они получают роль «Читатель». Администратор может менять роли в разделе «Управление».

Для фотографий сайт использует приватный бакет `wiki-images`. Читатель получает фото только из статей, к которым у него есть доступ. Максимальный размер файла — 10 МБ; поддерживаются JPG, PNG, WebP и GIF.

Сеанс входа хранится в текущей вкладке браузера. После закрытия вкладки может понадобиться войти заново. Если Supabase работает на собственном домене, добавьте этот адрес в `connect-src` политики CSP в [index.html](index.html) до публикации.

## Правила безопасности и хранения

- Записывайте ID подключений, но не пароли, одноразовые коды, ключи восстановления и другие секреты.
- Приглашённые читатели могут просматривать открытые записи; только администраторы создают, меняют и удаляют материалы.
- История статей сохраняется в Supabase. Порядок резервного копирования приведён ниже.
- Удаление статьи из интерфейса скрывает её для всех. История удалённой статьи остаётся в базе, но восстановление удалённых статей через интерфейс пока не предусмотрено.

Если у вас уже была локальная версия, сохраните её экспортом JSON перед переключением на Supabase. Автоматического переноса локальных записей в общую базу пока нет.

## Резервное копирование общей вики

Ручная копия включает дамп базы PostgreSQL (статьи, разделы, версии, записи пользователей и схемы БД) и файлы из приватного бакета `wiki-images`. Настройки проекта Supabase вне базы, например URL приглашений и параметры почты, сохраните отдельно. Скрипт [scripts/backup.py](scripts/backup.py) запускают **на своём компьютере или доверенном сервере**, не в браузере и не в GitHub Pages. Нужны Python 3.11+ и `pg_dump` версии не старше сервера Supabase. Задайте в окружении:

- `SUPABASE_DB_URL` — строка подключения к базе из Supabase → Connect. Используйте прямое подключение или session pooler, если прямой IPv6 недоступен. Не используйте transaction pooler.
- `SUPABASE_URL` — адрес проекта вида `https://<project>.supabase.co`.
- `SUPABASE_SERVICE_ROLE_KEY` — секретный ключ сервера из Supabase → Project Settings → API. Этот ключ обходит правила доступа, поэтому храните его только на доверенном устройстве и не вставляйте в `config.js`, репозиторий или переписку.

После установки переменных выполните:

```bash
python3 scripts/backup.py --output-dir /путь/к/приватным/копиям
python3 scripts/verify_backup.py /путь/к/приватным/копиям/wikihmru-ДАТА-ИДЕНТИФИКАТОР
```

Скрипт создаёт отдельный каталог с правами `0700`. В нём находятся `database.dump`, `images/` и `manifest.json` с контрольными суммами SHA-256. Копия содержит личные данные и может содержать секреты, внесённые в вики по ошибке. Храните её в зашифрованном месте с ограниченным доступом. Не добавляйте каталог копии в Git и не публикуйте его через Pages. Контрольные суммы проверяют целостность файлов, но не подтверждают, что неизвестный источник безопасен.

Для восстановления потребуется новый проект Supabase, совместимая версия `pg_restore` и загрузка файлов обратно в приватный бакет. Восстановление базы Supabase затрагивает системные схемы и учётные записи; сначала проверьте его на отдельном тестовом проекте и обратитесь к актуальной инструкции Supabase по восстановлению. Резервное копирование не создаёт согласованный снимок базы и Storage в одну секунду; во время копирования больших объёмов лучше не изменять статьи и фотографии.

### Автоматические копии с Supabase Pro

На тарифе Supabase Pro [автоматические резервные копии базы данных](https://supabase.com/docs/guides/platform/backups) создаются самим Supabase ежедневно. После подключения тарифа откройте раздел **Backups** своего проекта, проверьте появление успешной копии и доступный срок хранения в панели. Период хранения и возможность восстановления зависят от текущего тарифа и настроек проекта; не полагайтесь на предполагаемый срок без проверки в панели. Ежемесячное расписание для БД в GitHub Actions не требуется.

Копия БД содержит метаданные Storage, но **не содержит сами файлы фотографий**. Для фото из бакета `wiki-images` на доверенном компьютере или сервере выполните отдельный экспорт:

```bash
python3 scripts/backup.py --images-only --output-dir /путь/к/приватным/копиям
python3 scripts/verify_backup.py /путь/к/приватным/копиям/wikihmru-ДАТА-ИДЕНТИФИКАТОР
```

В режиме `--images-only` нужны только `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`; `pg_dump` и пароль БД не нужны. Скрипт автоматически проверяет контрольные суммы после выгрузки. Публичный репозиторий GitHub Pages не подходит для хранения копий.

### Ежемесячная копия на Windows

На тарифе Supabase Free используйте полную копию базы и фото на своём компьютере. Установите Python 3.11+ и клиент PostgreSQL 17+ с `pg_dump`, скачайте репозиторий WikiHMRU и в PowerShell из его папки выполните:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install-windows-backup.ps1
```

Установщик попросит публичный Project URL, секретный `service_role` key из Project Settings → API Keys и строку подключения к базе из кнопки **Connect** проекта. Для строки БД выберите **Session pooler** или прямое подключение, если оно доступно; Transaction pooler для `pg_dump` не подходит. Оба секрета вводятся скрыто и сохраняются в зашифрованном виде средствами Windows для текущей учётной записи в `%LOCALAPPDATA%\WikiHMRU\backup-config.json`. Они не отправляются в GitHub.

Установщик создаёт задачу **WikiHMRU-Monthly-Backup** в Планировщике задач Windows. Она запускается при входе в систему и ежедневно в 10:00 по местному времени, но создаёт копию только один раз за календарный месяц. Если компьютер был выключен или сеть не работала, задача повторит попытку при следующем входе или ежедневном запуске. Для работы пользователь должен войти в Windows. На тарифе Pro можно оставить автоматические копии БД Supabase и настроить только фото, добавив к команде установщика `-Mode ImagesOnly`.

Архивы сохраняются в `%LOCALAPPDATA%\WikiHMRU\backups`, а результат и ошибки записываются в `%LOCALAPPDATA%\WikiHMRU\backup.log`. Метка месяца обновляется только после успешной выгрузки и проверки файлов. Для первой проверки вручную запустите задачу через Планировщик задач или командой `Start-ScheduledTask -TaskName WikiHMRU-Monthly-Backup`, затем проверьте журнал и созданный каталог. Не удаляйте старые архивы, пока не определите срок хранения; место на диске нужно периодически проверять. Для защиты копий при потере компьютера включите шифрование диска Windows (BitLocker или шифрование устройства, если оно доступно).
